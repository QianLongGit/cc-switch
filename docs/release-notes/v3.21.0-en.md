# CC Switch v3.21.0

> This release brings one new capability: **routing providers per project**. When you work on several projects at once in Claude Code, each project can stick to its own provider: CC Switch discovers your project list automatically by merging three sources under `~/.claude` and computing activity, you bind a project to a provider on the new "Project Routing" page, and the binding is written into the project's own `.claude/settings.local.json`; requests sent through the local proxy carry the `X-CC-Project` marker and prefer the bound provider. The binding is *soft*: when the bound provider fails, requests fall back to the shared failover queue in order; when everything is tripped, the shared queue still rescues; and when the bound provider is deleted, routing reverts automatically. The request log gains a project column, a "Routed" badge and a project filter, and requests that took the vision branch now carry an "[Image]" badge. The first phase covers the Claude app only and requires proxy takeover to be enabled. **This release includes a database migration (v19 → v21); we recommend backing up the database manually before upgrading** — see [Upgrade Notes](#this-release-includes-a-database-migration).

## Highlights: What You Can Do Now

- **Pin a provider to each project**: a new "Project Routing" page (a Claude-app-only entry, between the session browser and MCP buttons). One row per project: project name, last activity, a provider dropdown and a sync status. Picking "Default (no binding)" returns to global routing.
- **Register projects without lifting a finger**: the project list is discovered from three sources under `~/.claude` — the `projects` key of `~/.claude.json` (the authoritative path list), the session jsonl files under `~/.claude/projects/*/`, and the activity markers in `~/.claude/sessions/*.json` — sorted by activity, with anything inactive for over 30 days left out; the page refreshes every 3 seconds while open.
- **A failed binding never blocks you**: soft-binding semantics. With failover on, the bound provider leads the candidates with the shared queue deduplicated behind it; if the bound provider fails or is tripped open, requests degrade to the shared queue; when everything is tripped the shared queue still rescues; and after the bound provider is deleted, routing reverts to the shared queue and the page shows the binding as invalid instead of silently clearing it.
- **See which project a request came from**: the request log gains a project column, a "Routed" badge for requests that hit a project binding, and a project filter.
- **Tell bindings and files apart at a glance**: three sync states (synced / out of sync / orphan header), with one-click repair for "out of sync" and an optional cleanup for orphan headers.
- **Spot vision-branch requests**: requests routed through the vision branch now show an "[Image]" badge in the model column of the request log.

## Overview

"Routing providers per project" removes the switching friction of running several projects at once: provider selection used to be globally unique per app, so changing projects meant switching cards. Now every Claude Code session carries its own project identity — CC Switch injects a single `X-CC-Project: <percent-encoded path>` line into the multi-line value of `env.ANTHROPIC_CUSTOM_HEADERS` in the project's `.claude/settings.local.json` — and the local proxy routes requests carrying that marker to the provider bound to the project.

The write is deliberately conservative: only the `X-CC-Project` line is added, replaced or removed; your own other header lines, every other env key and every top-level key in the file are preserved byte for byte. A missing file starts from a minimal structure; a corrupted JSON is rebuilt as an empty object only after the original text is backed up to the database (one most-recent snapshot per project); and writes land through a temp file plus atomic rename. Binding and unbinding are both "database first, then file" double writes; if the file write fails, the database row stays and the sync status drives the repair.

The routing semantics are a soft-binding four-quadrant matrix: unbound requests behave exactly as before; with failover off and a binding present, only the bound provider is used; with failover on and the bound provider healthy, it leads and the shared queue follows deduplicated, degrading on failure; with the bound provider's breaker open, it steps aside entirely for the shared queue — in other words, a binding only moves a provider to the front of the line and can never disable the shared rescue queue. A failed binding lookup itself (a database error) also degrades to unbound routing instead of blocking the request.

The request log records two new attribution fields per entry, `project_dir` (the source project path) and `project_routed` (whether a project binding was hit), surfaced as a project column, a "Routed" badge and a project filter; the same migration also adds `vision_routed` (the vision-branch marker), shown as an "[Image]" badge in the model column. This release includes a database migration: `SCHEMA_VERSION` 19 → 21, adding the `project_routes` table (project → provider bindings) and the `settings_local_backup` table (pre-write snapshots of settings.local.json), plus new columns on the request log table.

## Added

### Routing Providers per Project

The first phase covers the Claude app only (`app_type` `claude`); the entry button appears only while the Claude app is active. Binding requires local proxy takeover: the `X-CC-Project` marker travels on proxied requests, so without takeover (direct connection) a binding changes nothing and no existing behavior is affected.

- **Project discovery**: three read-only sources, merged. The `projects` key of `~/.claude.json` is the authoritative path list (`lastSessionModified` provides activity); the `*.jsonl` files under `~/.claude/projects/*/` provide a supplementary cwd and file-mtime activity — stale directories without a jsonl do not count as projects; and `~/.claude/sessions/*.json` mark currently active sessions (`busy`/`idle` and friends). The sources merge by path taking the maximum activity, drop projects whose directory no longer exists or that have been inactive for over 30 days, and sort by activity descending. A missing or corrupted `~/.claude.json` degrades gracefully to the jsonl source.
- **Binding UI**: each project row shows the basename (full path on hover), an "in use" badge (active session), a relative activity time (absolute time on hover), a provider dropdown (including "Default (no binding)") and a sync badge. The page polls every 3 seconds while open and stops as soon as you navigate away.
- **Binding writes**: binding = a `project_routes` row in the database plus the `X-CC-Project` line in the project's `.claude/settings.local.json`, written together; unbinding clears both (silently succeeding when the file or the target line is missing — idempotent). The path is percent-encoded at the UTF-8 byte level (unreserved `[A-Za-z0-9/._~-]`, everything else as `%XX`), so the encoded value is always a single line — newlines and other header-syntax-sensitive bytes are always escaped. Binding to a nonexistent provider fails immediately, leaving no dangling row.
- **Soft-binding routing matrix**: see the Overview above. A healthy bound provider leads with the shared queue deduplicated behind it; a tripped bound provider or a failed binding lookup steps aside for the shared queue; the unbound path is byte-for-byte identical to before.
- **Deletion cascade**: after the bound provider is deleted, the project's requests route to the shared queue as if unbound; the page shows such dangling bindings as "provider name · invalid" without silently clearing them — rebind or switch back to default to clear the warning.
- **Three sync states and one-click repair**: `synced` (database binding matches the file), `out_of_sync` (the database has a binding but the file is missing, lacks the target line or holds a different value — one click rewrites the file line from the database binding) and `orphan_header` (the database has no binding but the file still carries the target line; that line does not participate in routing — it is only flagged, and clearing it is up to you).

### Project Attribution and Filtering in the Request Log

Every proxied request now records its source project path and whether a project binding was hit. The request log table gains a project column, requests that hit a binding carry a "Routed" badge, and the list can be filtered by project; the request detail panel shows the same fields. The fields do not participate in the existing semantic hash, so old data is unaffected.

### "[Image]" Badge in the Request Log

Requests that took the vision branch were previously indistinguishable from ordinary ones in the model column; they now carry an "[Image]" badge, with the model chain shown as "[Image] actual model". Older records have no marker and display without the badge.

## Upgrade Notes

### This release includes a database migration

`SCHEMA_VERSION` 19 → 21, in two steps: v19 → v20 adds the `vision_routed` column to `proxy_request_logs`; v20 → v21 adds `project_dir` and `project_routed` to it. Two new tables are created as well: `project_routes` (project → provider bindings, at most one per project per app) and `settings_local_backup` (pre-write snapshots of settings.local.json, one most-recent snapshot per project). The migration runs automatically on first launch. After running this version once, v3.20.4 and earlier refuse to open the database as too new — downgrading requires restoring a backup made before the upgrade. To be safe, quit CC Switch first and copy the database manually:

```bash
cp ~/.cc-switch/cc-switch.db ~/cc-switch-before-v3.21.0.db
```

On Windows the default path is `%USERPROFILE%\.cc-switch\cc-switch.db`. If you have changed the config directory in Settings, the database lives there.

### Claude app only, and proxy takeover required

Project routing applies to the Claude app only (Codex, Gemini and friends are not covered yet), and requests are attributed by `X-CC-Project` only when they go through the local proxy (takeover enabled). In direct-connection mode a binding changes no behavior.

### Bindings and unbindings take effect for new sessions

`settings.local.json` is read by Claude Code when a session starts: after binding or unbinding, start a **new session** (reopen Claude Code in the project) for the new header to be sent. Existing sessions keep sending the environment they started with.

### How settings.local.json is modified

CC Switch touches only the `X-CC-Project` line within the multi-line `env.ANTHROPIC_CUSTOM_HEADERS` value; your other headers, other env keys and top-level keys are preserved byte for byte. A corrupted file is rebuilt as an empty object only after the original text is backed up to the database; a pre-write snapshot is saved before every write (one most-recent snapshot per project). All writes land atomically — no half-written states.

### Unbound projects behave exactly as before

With no bindings at all, routing is identical to v3.20.4; the `orphan_header` hint appears only if you bind and then edit the file by hand, and clearing it never touches anything else in the file.
